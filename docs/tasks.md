Зберегти існуючі програмні I²C/SPI backend як початковий варіант super loop. Не вважати їх block-free: одна SD write/read у bring-up займала833 мс MCU часу, читання410–411 мс. Це спостереження ЛР2, не S3-baseline ЛР3. Майбутні спроби оптимізації мають випливати з невиконаної вимоги чи підтвердженої помилки.

## Реальне сховище

Вибір: SDHC raw-сектори, без FAT/malloc. Scratch32 доведений записом/читанням; після export образ завантажено в інший процес Wokwi і sdread повернув512 збіжних байтів без запису. Перед реалізацією журналу зафіксувати layout: 512 записів по64 байти; буфер512, журнал у виділених секторах128–255, два metadata-сектори126/127 з sequence/CRC. Подвійні metadata не роблять atomicity автоматично: power-loss перевіряється на кожній фазі запису. Незаписаний/пошкоджений слот ігнорується, ACTIVE з попереднього boot завершується INTERRUPTED/POWER_LOSS. Demo image writable окремо від незмінних evidence images. Фізична карта і brownout не перевірені.

## Сценарії майбутньої ЛР3

S1:60 000 мс MCU, sample25 °C, ambient24 °C, кришка закрита, без партій/команд; періодичні виміри активні.

S2:3 600 000 мс одного неперервного MCU інтервалу. Повторюваний120-секундний цикл: start, sample25→60 °C до10-ї секунди, тримати≥30 с у[58,62], cool до35 °C до70-ї секунди, DONE і наступна партія. ambient24 °C; status раз/10 с; запис усіх переходів. Автоматичний collector перевіряє boot count, послідовність timestamp/record seq, error counters і CRC. Початковий контроль≤10 хв; далі один wakeup на оцінений залишок, з перерахунком за MCU elapsed. Перервані запуски не складаються в годину.

S3:60 000 мс MCU; export заповненого журналу, SD write, опитування та status10/с; ≥30 фізичних відкриттів під час довгих операцій, закриття перед новою партією. Програма-генератор має зберігати момент зміни модельного входу і отриманий результат. Окремо піднімати частоту status 2→10→20→50/с до першого порушення; зберегти failed run, не змінювати дедлайн для приховування межі.

Окремі обов’язкові перевірки §6.2: NACK 0x76 і recover; утримання SDA LOW/повернення; startup з неготовим сенсором; UART overflow; тривала робота; перезапуск під час реальної SD-запису. Зупинка процесу симулятора сама по собі не доводить фізичне зникнення живлення; якщо модель не дозволяє відповідного зриву, статус недоступний із причиною, а не pass.

## Інструменти і порівняння

На M0+ немає DWT CYCCNT. Для ЛР3 налаштувати TIM3 1 MHz, unsigned wrap-aware deltas/розширення часу, перевірити проти GPIO VCD і HAL ms. Вимірювати кожну задачу, loop, latency, jitter, missed, CPU busy vs idle, startup, статичні секції та stack painting. Heap продукту0; C library heap зарезервований linker-скриптом не означає використання0 без перевірки. Одну метрику отримати двома методами, навести min/avg/max/p99 та межі методу. Зберегти scripts, raw UART/VCD, stimuli, ELF/HEX hashes, версію профілю. Лише після цих експериментів створювати docs/baseline-lab4.md і реєстр щонайменше5 фактичних обмежень.

ЛР4: офіційний FreeRTOS ARM_CM0 порт, той самий продукт/CLI/профілі, buildable lab3. Повторити обидві версії на тому самому стенді в один день. Додати6 OS експериментів §7.2: priority inversion mutex/semaphore, stack overflow з/безhook, starvation, queue exhaustion, heap exhaustion, tick100/1000 Hz. Оцінити tick/context-switch/ISR→task, стеки, heap, flash/RAM ядра, складність. Перевірити всі гіпотези ЛР3, зокрема можливі втрати пам’яті/часу startup. FreeRTOS зараз не підключено. Методички ЛР5–6 відсутні.

Поточна реалізація ЛР3 та фактичний план вимірювань: [lab3-tasks.md](lab3-tasks.md). Наведений вище metadata-sector варіант був проєктним; схема журналу ЛР3 описана у новому файлі.
